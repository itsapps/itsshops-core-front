# Translations & URLs (frontend)

How UI strings and URL segments are translated, and how a customer overrides them.

## Two namespaces, two core files per locale

`setupTranslation` (`src/i18n/translations/frontTranslation.ts`) loads core resources:
- **`common`** ← `de_11ty.ts` / `en_11ty.ts` — UI strings used in templates (navigation, language
  switch, skip links, …). This is the **default namespace**.
- **`shared`** ← `de_shared.ts` / `en_shared.ts` — strings shared with client/server code, including
  **`urlPaths`** (the user/account/newsletter/withdraw URL segments).

**Core ships `de` + `en` only.**

## Form of address: "Sie" base + "Du" overlays

The German base files (`de_11ty.ts`, `de_server.ts`, `de_shared.ts`) are **"Sie"**. Overlay files
`de_11ty.informal.ts` / `de_server.informal.ts` / `de_shared.informal.ts` hold only the keys whose
"Du" text differs (same nesting). `SHOP_FORMALITY=informal` (env, see
[configuration.md](configuration.md)) merges them over the base — on the website in
`frontTranslation.ts` (before the shop's `config.translations`), in the functions in
`netlify/utils/i18n.ts` (`serverT`, read per call). English is unaffected.

When adding a German string that addresses the reader: write it in "Sie" in the base **and** add the
"Du" variant to the matching overlay (a test checks overlay keys ⊆ base keys, not tone). Statutory
texts follow the setting too — the overlay changes only the address forms. Shop `config.translations`
overrides reach the website only, never the emails.

## Resolution & override (`src/i18n/translations/t9n.ts`)

`createTranslator(config, coreResources)` builds the i18next instance:
- For each `config.locales`, it **deep-merges** (`lodash.merge`) the core base with
  `config.translations[locale]` — **project overrides win**.
- `defaultNS: 'common'`, `fallbackLng: config.defaultLocale`, `supportedLngs: config.locales`.
- ⚠️ **A missing key throws** (`missingKeyHandler`) and surfaces as an Eleventy build error — every
  key referenced in a template must exist in some locale. In debug mode, missing interpolation values
  also throw.

### Overriding a core string
Pass `config.translations` keyed by locale → namespace → key path:

```ts
// itsshops.config.mts
translations: {
  de: {
    common: { navigation: { goHome: 'Zur Startseite von Weingut X' } },
    shared: { urlPaths: { userLogin: 'login' } },   // changes the /login URL segment
  },
  en: { /* … */ },
}
```
Only the keys you set are replaced; everything else falls back to core.

## Using translations in templates

`createFilters` (`src/filters/index.ts`) registers the **`trans`** filter, which resolves against the
current page locale (`this.page.lang`, else `defaultLocale`):

```njk
{{ 'navigation.goHome' | trans }}
{{ 'some.key' | trans({ name: winery }) }}   {# with interpolation params #}
```
Internally `translate(key, params, locale)` is also on `CoreContext` for filters/shortcodes.

## URL segments: two separate systems

Changing a URL segment depends on which kind:

| Segment kind | Controlled by | Where |
|---|---|---|
| Content types (product, category, blog) + checkout / order thanks | `config.permalinks` → `buildPermalinkTranslations` → `resolvedPermalinks` | `src/i18n/permalinks.ts` |
| User / account / newsletter / withdraw | `translations.<locale>.shared.urlPaths` → `buildUserPaths` | `src/i18n/permalinks.ts` reads the `shared` resources |

So e.g. the product listing segment is a `permalinks` override, but the login/checkout-account
segments are `shared.urlPaths` translation overrides. Both are per-locale.

## Adding a locale

1. Add it to `config.locales` (and set `defaultLocale` if needed).
2. Provide **full** `common` + `shared` resources for it under `config.translations` — core has no
   base for non-de/en locales, so any unprovided key throws at build time.
